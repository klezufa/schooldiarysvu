# Резервное копирование и восстановление

Копия без проверенного восстановления — это надежда, а не копия. Ниже: что копируется, как настроить
ежедневное копирование и вторую копию на другом носителе, как восстановить данные и как регулярно проверять,
что восстановление работает.

Скрипты для сервера Linux — `scripts/backup.sh` и `scripts/restore.sh`. Для Windows 11 — `diary.cmd backup` /
`diary.cmd restore` (запуск без Docker) и `deploy\windows\docker-data.cmd` (Docker Desktop), см.
[windows-local.md](windows-local.md). Все варианты записывают результат в журнал эксплуатации, который
системный администратор видит на странице **«Система» → «Эксплуатация»**: дату и размер последней копии,
причину последней неудачи. Предупреждение появляется, если копии нет больше 26 часов.

## Что входит в копию

Каталог `diary-ГГГГММДД-ЧЧММСС`:

| Файл | Содержимое |
| --- | --- |
| `database.dump` | вся база (`pg_dump -Fc`): пользователи, журнал, расписание, оценки, аудит, настройки |
| `files.tgz` | вложения (домашние задания, файлы учителей) из тома `files-data` |
| `manifest.json` | время, проект, версия схемы БД, коммит кода, признак согласованности, размер |
| `SHA256SUMS` | контрольные суммы; восстановление их проверяет |

Не входит и хранится отдельно: `.env` (новый сервер можно поднять с новым паролем PostgreSQL — дамп
восстанавливается в любую базу), сертификат и ключ (`TLS_DIR`), `/etc/schooldiary/lego.env` с ключом API DNS.
Ключ API и корневой ключ ЦС **не кладите** рядом с копиями дневника.

Копия содержит персональные данные учеников, родителей и сотрудников. Храните её так же строго, как сам сервер:
доступ только у ИТ-администраторов, шифрованный носитель или хранилище, срок хранения по положению школы
об обработке персональных данных; старые копии удаляются автоматически (`BACKUP_KEEP`).

## Создание копии

```bash
cd /opt/schooldiary
sudo bash scripts/backup.sh             # «на ходу», без остановки
sudo bash scripts/backup.sh --quiesce   # согласованная: nginx, worker, backend остановлены на 10–60 секунд
```

Без `--quiesce` база согласована внутри себя (снимок PostgreSQL), но вложение, загруженное во время копирования,
может попасть в архив файлов без записи в базе или наоборот. Для ночного задания используйте `--quiesce`.

Скрипт:

- отказывается копировать, если PostgreSQL не запущен или миграция базы прервана (`dirty`);
- собирает копию в `.diary-….partial` и переименовывает только после проверки контрольных сумм — каталог без
  `.partial` всегда полный;
- при любой ошибке не оставляет частичной копии, перезапускает остановленные сервисы, пишет причину в
  `BACKUP_DIR/backup.log` и в журнал эксплуатации и завершается с ненулевым кодом;
- оставляет `BACKUP_KEEP` последних копий (14 по умолчанию); страховочные копии `pre-restore-…` считаются отдельно.

Переменные (для cron — в `/etc/default/schooldiary`, [installation.md](installation.md#7-расписание-обслуживания)):

| Переменная | По умолчанию | |
| --- | --- | --- |
| `BACKUP_DIR` | `/opt/schooldiary/backups` | каталог копий на сервере |
| `BACKUP_KEEP` | 14 | сколько копий хранить на сервере |
| `BACKUP_REMOTE` | — | куда отправлять вторую копию |

## Вторая копия на другом носителе

Копия на том же диске не защищает от отказа диска, шифровальщика или кражи сервера. `BACKUP_REMOTE`:

- **каталог** (смонтированный NAS, второй диск): `BACKUP_REMOTE=/mnt/nas/schooldiary` — копия переносится
  и проверяется по контрольным суммам на месте;
- **другой сервер по SSH**: `BACKUP_REMOTE=backup@nas.school.lan:/volume1/schooldiary` — через `rsync`.
  Создайте для root отдельный ключ `ssh-keygen -t ed25519 -f /root/.ssh/schooldiary-backup -N ''`,
  в `/root/.ssh/config` укажите его для этого хоста, а на принимающей стороне ограничьте ключ
  (`restrict` в `authorized_keys`, отдельный пользователь без shell с правом записи только в свой каталог).

Удаление старых копий на принимающей стороне настраивается там же (NAS: правило хранения или snapshot);
хорошо, если сервер дневника не может удалять или перезаписывать уже переданные копии — так шифровальщик
на сервере не уничтожит и их.

## Восстановление

```bash
cd /opt/schooldiary
sudo bash scripts/restore.sh /var/backups/schooldiary/diary-20261101-023000
```

Порядок работы скрипта:

1. Проверяет контрольные суммы и версию схемы: копию, сделанную более новой версией дневника, чем установленный
   код, он не восстанавливает (сначала обновите код до той версии). Копию со старой схемой — восстанавливает,
   backend при запуске применит недостающие миграции.
2. Показывает, что будет заменено, и ждёт ввода `YES`.
3. Делает страховочную копию текущего состояния `pre-restore-…`.
4. Останавливает nginx, worker, backend.
5. Восстанавливает базу во **временную** БД; рабочая база заменяется только после успешного `pg_restore`.
   Если копия повреждена, текущие данные не меняются.
6. Завершает все сессии (вход заново для всех), восстанавливает вложения, запускает приложение и ждёт готовности.
7. Пишет результат в журнал эксплуатации и печатает список проверок.

Если восстановление не удалось, скрипт перезапускает приложение и сообщает, где лежит страховочная копия;
вернуть исходное состояние — `sudo bash scripts/restore.sh <каталог pre-restore-…>`.

Что помнить после восстановления: всё, что внесено после времени копии (оценки, записи журнала, новые
пользователи), потеряно — сообщите учителям дату копии. Пароли, изменённые после неё, снова прежние.

### Восстановление на новый сервер

Установите дневник той же или более новой версии по [installation.md](installation.md) (шаги 1–5, без создания
администратора — он придёт из копии), перенесите каталог копии на сервер и выполните `restore.sh`.

## Проверка восстановления

Раз в месяц (и после каждого обновления версии) восстанавливайте последнюю копию на **отдельном тестовом
сервере** или виртуальной машине, не трогая рабочий:

```bash
sudo bash scripts/restore.sh /mnt/nas/schooldiary/diary-20261101-023000 --yes
```

и проверяйте: вход администратора; журнал любого класса за последние дни перед копией; открывается вложение;
число пользователей на странице администрирования совпадает с рабочим сервером. Запишите дату проверки и
время восстановления — это реальное время простоя при аварии.
