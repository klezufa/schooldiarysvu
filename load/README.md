# Нагрузочное тестирование

Сценарий k6 «учебное утро» на школе в 360 учеников, 360 родителей и 150 учителей. Проверяет производственную
конфигурацию: Docker Compose, Nginx, лимиты памяти контейнеров.

## Данные

Нагрузочный набор строится поверх базового демо (`cmd/seed/demo_load.sql`, `DEMO_DATASET=load`):

- 12 классов (6А–9В) по 30 учеников, у каждого ученика родитель;
- 150 учителей: 120 ведут уроки (у пары «класс — предмет» свой учитель), 12 — классные руководители;
- 10 предметов, недельная сетка 6 уроков × 5 дней, уроки с 1 сентября до двух недель вперёд;
- около 3 900 уроков, 35 000 оценок, 95 000 отметок посещаемости, 1 400 домашних заданий (база ~52 МБ);
- пароль у всех — `DEMO_PASSWORD`, без обязательной смены.

Только для локальной или тестовой машины: сид отказывается работать при `APP_ENV=production`.

## Запуск

```bash
# Стек и данные (backend в production, сид — одноразово с APP_ENV=development)
docker compose -p diaryload --env-file .tmp/load/compose.env up -d --build
DEMO_PASSWORD='<пароль от 12 символов>' docker compose -p diaryload --env-file .tmp/load/compose.env run --rm --no-deps \
  -e APP_ENV=development -e ALLOW_DEMO_SEED=true -e DEMO_PASSWORD -e DEMO_DATASET=load --entrypoint /app/seed backend

# Данные для сценариев — из той же базы, что тестируется
docker compose -p diaryload --env-file .tmp/load/compose.env exec -T postgres \
  sh -c 'PGCLIENTENCODING=UTF8 psql -At -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < load/fixtures.sql > .tmp/load/fixtures.json

# Сценарии (k6 — в .tools/k6; профили: smoke, morning, logins)
cd load
PASSWORD='<тот же пароль>' FIXTURES=../.tmp/load/fixtures.json BASE_URL=http://127.0.0.1:8086 PROFILE=morning k6 run school-day.js
```

Профили:

| Профиль | Что делает |
| --- | --- |
| `smoke` | по 3 пользователя каждой роли, 2 итерации — проверка сценария |
| `morning` | за 3 минуты собираются 120 учителей, 300 учеников и 180 родителей (600 одновременно), ещё 5–6 минут работают: учитель — «Сегодня», журнал, оценка, «все присутствуют», дашборд; ученик и родитель — расписание, объявления, дашборд, оценки, задания |
| `logins` | только входы, частота растёт до 20 в секунду — предел хеширования паролей |

Пороги: ошибок < 1 %, чтение p95 < 500 мс, запись p95 < 800 мс, вход p95 < 2 с. Ответ 409 на оценку — ожидаемый
(работу уже оценил другой виртуальный учитель) и считается отдельно (`grade_conflicts`).

## Результаты (1 ноября 2026, Docker Desktop на рабочей станции, Compose как в production, PostgreSQL 17.6 → 17.11)

| Проверка | До исправления | После |
| --- | --- | --- |
| `logins`: ошибки входа | **58 %** | 0 % |
| `logins`: OOM и перезапуски backend | **5 перезапусков за 2 минуты** | 0 |
| `logins`: пик памяти backend | 512 МиБ (упор в лимит) | 292 МиБ |
| `logins`: вход p95 при 20 входах/с | — | 3,7 с (очередь хешей) |
| `morning`: запросов / ошибок | — | 50 440 / 0 |
| `morning`: чтение p95 / запись p95 / вход p95 | — | 60 мс / 29 мс / 247 мс |
| `morning`: пик памяти backend / PostgreSQL / Nginx | — | 360 / 231 / 14 МиБ |

Найденная проблема: каждый вход считает Argon2id с 64 МиБ памяти, и одновременные входы складывались — утренний
наплыв доводил контейнер с лимитом 512 МиБ до OOM, а перезапуск обрывал запросы всех, кто уже работал. Исправление:
не больше `PASSWORD_HASH_CONCURRENCY` (по умолчанию 2) хешей одновременно, остальные входы ждут в очереди до 10 секунд,
затем получают 503 с `Retry-After`; `GOMEMLIMIT` у backend и worker заставляет сборщик мусора держаться ниже лимита.

Пропускная способность входов при двух слотах — около 11 в секунду на этой машине; 600 входов растягиваются примерно
на минуту. На сервере с большим числом ядер и памяти `PASSWORD_HASH_CONCURRENCY` можно поднять (каждый слот — 64 МиБ).
